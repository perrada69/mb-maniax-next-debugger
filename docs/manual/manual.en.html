Contents

Introduction

MB Maniax Next Debugger is an extension for Visual Studio Code (VS Code from here on) that adds a ZX Spectrum Next emulator and a debugger to the editor. A program built with sjasmplus runs in an emulator based on the JNEXT core and you debug it right in its source code: stop it on a line, inspect registers and memory, step instruction by instruction – with the emulator screen next to your code.

If you are used to CSpect or DeZog, much of this will feel familiar: the CSpect BREAK instruction works, and the special comments WPMEM, LOGPOINT and ASSERTION use the same syntax as DeZog. The difference is that there is nothing else to install or start – the emulator is part of the extension.

Features

  • Source breakpoints based on the sjasmplus debug information (the SLD file), including the Next's 8K pages – a breakpoint in paged code stops only when its page is mapped in.
  • Conditional breakpoints with no slowdown – the condition (A == 5, mem[counter] == 3, nextreg[$50] == 10, FRAME > 100 …) is evaluated by the emulator itself. Labels from the source can be used directly.
  • Hit counts (3, >= 10, % 4) and logpoints, which print a message with values instead of stopping.
  • Machine event breakpoints: IM 1 / IM 2 interrupts, NMI, NEXTREG writes, port input/output, Copper, DMA, reset.
  • Watchpoints – stop on a memory read or write.
  • Stepping (Step Into / Over / Out), call stack with labels, registers and flags (editable), MMU pages, disassembly, memory viewer and editor, expressions in the Watch view and on hover.
  • Step Back – the emulator remembers the last 10 seconds.
  • Start into NextZXOS – the emulator boots the real NextZXOS and you debug the program NextZXOS starts (NextZXOS is downloaded from specnext.com on request).
  • WiFi – the emulated ESP-01 module opens real network connections; network programs can be debugged against servers on your LAN or on the internet.
  • Emulator screen in a VS Code panel, with sound and keyboard.
  • Next panel with views of the hardware: sprites, Pattern RAM, palettes, layers, Layer 2, tilemap, the Copper program and all NEXTREG registers.
  • Saved states of the whole machine, and export to a file.
  • Profiler showing how many T-states the program spent on every source line.

Requirements

  • Windows (x64) – the extension package mbx-next-debugger-win32-x64-0.1.0.vsix contains the debug server for 64-bit Windows.
  • Visual Studio Code 1.100 or newer.
  • sjasmplus – the assembler you build the program with. It should be on the PATH, so that the command sjasmplus works in a terminal.
  • No SD card and no Next ROMs are needed: the extension has its own ZX Spectrum 48K ROM and starts the program directly. An SD card with ROMs is only needed to emulate machines other than the Next (see ).

Installation

The extension comes as a single file with the .vsix extension (for example mbx-next-debugger-win32-x64-0.1.0.vsix). It is a package VS Code installs by itself – do not unpack it.

Installing from a .vsix file

  1. Start VS Code.
  2. Open the Extensions view: in the narrow vertical strip of icons on the far left (the Activity Bar) click the icon with four squares, or press Ctrl+Shift+X. The Extensions list opens on the left.
  3. In the header of the list (top right, above the search box) click the three dots … (Views and More Actions) and choose Install from VSIX….
  4. Select the .vsix file in the dialog and confirm with Install. A notification in the bottom right corner reports when installation is complete.

The same is available from the Command Palette: Ctrl+Shift+P, type vsix and choose Extensions: Install from VSIX…. From the command line:

code --install-extension mbx-next-debugger-win32-x64-0.1.0.vsix

Updating to a new version

A new version is installed exactly the same way – install the new .vsix; there is no need to uninstall the old one first. If a debug session is running, stop it first (Shift+F5). After installation VS Code usually offers a button to restart extensions; if it does not, or you are not sure the new version is running, reload the window (next section).

Reloading the window (Developer: Reload Window)

After installing or updating the extension, the safest step is to reload the window – VS Code reloads all extensions, while open files and the window layout stay as they are:

  1. Press Ctrl+Shift+P (or F1). The Command Palette input box opens at the top centre of the window.
  2. Type reload.
  3. Choose Developer: Reload Window and press Enter.

The window disappears for a moment and is drawn again. Closing and restarting VS Code works too.

Checking the installation

In the Extensions list (Ctrl+Shift+X) type MB Maniax into the search box. MB Maniax Next Debugger with its version number should be listed among the installed extensions (Installed). Click it to open its description page.

Variables – registers and machine state

The Variables section of the Run and Debug side bar shows the machine state whenever the program is stopped. It has four groups:

  • Registers – AF BC DE HL IX IY SP PC in hex and decimal ($8000 (32768)), followed by the label the value points to (start, main_loop+3); then I, R, the interrupt mode IM and IFF1.
  • Flags – S Z H P/V N C as 0 or 1.
  • Shadow registers – AF' BC' DE' HL' (collapsed by default).
  • Machine (MMU, time) – Frame (frame number since start), Total T-states and the eight MMU slots: MMU0 ($0000) … MMU7 ($E000) with the number of the 8K page mapped into the slot (page 10 ($0A)).

Register and flag values can be changed ().

Watch

The Watch section holds expressions you want to keep an eye on – for example mem[counter] or HL. Add them with the + button in the section header (it appears when you hover over the header), or select text in the editor, right-click and choose Add to Watch. The values are recalculated every time the program stops. Details in .

Call Stack

The Call Stack section shows where the program is stopped and how it got there: the current location at the top (the name of the nearest label), below it the places subroutines were called from. The section header also shows the reason for stopping – for example Paused on breakpoint, Paused on step, Paused on BREAK or the name of an event.

Your first program

In this chapter you build and run the example program hello from the examples/hello folder. The program changes the border colour and counts in memory how many times it did so. The procedure is the same for your own project.

; examples/hello/hello.asm (shortened)
        DEVICE ZXSPECTRUMNEXT
        SLDOPT COMMENT WPMEM, LOGPOINT, ASSERTION
        ORG $8000
start:  ei
        ld sp, stack_top
        nextreg $07, 3          ; 28 MHz
        ld a, 0
        ld (counter), a
main_loop:
        call next_colour
        ld b, 25
.wait:  halt
        djnz .wait
        jr main_loop
next_colour:
        ld a, (counter)
        inc a
        and 7
        ld (counter), a
        out ($fe), a
        ret
counter:    db 0
            ds 64
stack_top:
        SAVENEX OPEN "hello.nex", start, stack_top
        SAVENEX CORE 3, 0, 0
        SAVENEX AUTO
        SAVENEX CLOSE

Building with debug information

For the debugger to know which source line corresponds to which address, it needs an SLD file (Source Level Debugging) from sjasmplus. sjasmplus writes it with the --sld option:

sjasmplus --sld=hello.sld --fullpath hello.asm
  • --sld=hello.sld – writes the debug information (lines, addresses, 8K pages, labels, keywords from comments).
  • --fullpath – writes full source paths into the SLD, so the extension reliably matches lines with the files open in the editor (even when the source is split into several files with INCLUDE).

The program itself (hello.nex) is written by the SAVENEX directive in the source.

Check that sjasmplus can be started: open a terminal (Ctrl+`) and type sjasmplus --version. If Windows does not know the command, add the sjasmplus folder to the PATH variable (then close and restart VS Code), or put the full path to sjasmplus.exe into tasks.json.

Opening the folder

VS Code works with folders (workspaces), not single files – debug and task settings are looked up in the .vscode subfolder of the open folder.

  1. Menu File › Open Folder… (Ctrl+K Ctrl+O) and select the examples\hello folder.
  2. If VS Code asks whether you trust the authors of the folder (Do you trust the authors…), confirm with Yes, I trust the authors – otherwise it would not be allowed to run tasks (the build).
  3. In the Explorer on the left (Ctrl+Shift+E) click hello.asm; it opens in the editor.

The launch.json file – how to debug

The .vscode/launch.json file tells VS Code what to start on F5. The example already has one:

{
    "version": "0.2.0",
    "configurations": [
        {
            "type": "mbx-next",
            "request": "launch",
            "name": "Ladit hello.nex",
            "program": "${workspaceFolder}/hello.nex",
            "sld": "${workspaceFolder}/hello.sld",
            "stopOnEntry": true,
            "preLaunchTask": "sjasmplus"
        }
    ]
}
  • "type": "mbx-next" – debug with this extension.
  • "name" – the name shown in the list next to the green ▶ button (in the example it is Czech, “Debug hello.nex”; use any name you like).
  • "program" and "sld" – the built program and its debug information; ${workspaceFolder} is the open folder.
  • "stopOnEntry": true – stop at the program's first instruction.
  • "preLaunchTask": "sjasmplus" – before starting, build the program with the sjasmplus task from tasks.json (next section).

For your own project create launch.json like this: in the Run and Debug side bar click create a launch.json file and choose MB Maniax Next Debugger. You get a configuration “Debug on ZX Spectrum Next” with program.nex and program.sld – replace the names with yours. To add another configuration to an existing launch.json, click Add Configuration… at the bottom right of the launch.json editor and choose MB Maniax Next Debugger: Next program (sjasmplus). All attributes are described in .

The tasks.json file – how to build

A task is a command VS Code runs for you – here the sjasmplus build. The example's .vscode/tasks.json:

{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "sjasmplus",
            "type": "shell",
            "command": "sjasmplus",
            "args": ["--sld=hello.sld", "--fullpath", "--lst=hello.lst", "hello.asm"],
            "options": { "cwd": "${workspaceFolder}" },
            "group": { "kind": "build", "isDefault": true },
            "problemMatcher": {
                "owner": "sjasmplus",
                "fileLocation": ["autoDetect", "${workspaceFolder}"],
                "pattern": {
                    "regexp": "^(.*)\\((\\d+)\\):\\s+(error|warning)[^:]*:\\s+(.*)$",
                    "file": 1, "line": 2, "severity": 3, "message": 4
                }
            }
        }
    ]
}
  • "label" – the task name; preLaunchTask in launch.json refers to it.
  • "args" – sjasmplus options (--lst also writes a listing).
  • "group": … "isDefault": true – the default build task: run it any time with Ctrl+Shift+B, even without debugging.
  • "problemMatcher" – sjasmplus errors and warnings appear in the Problems tab and as squiggles in the source.

Starting: F5

  1. Press F5. The Terminal opens in the bottom panel and the build runs. (If the build fails, VS Code offers Debug Anyway or Show Errors – look into Problems.)
  2. The emulator starts and the ZX Spectrum Next panel with the screen opens to the right of the editor.
  3. Because the example has "stopOnEntry": true, the program stops right at its first instruction (ei after the start label) – the line is yellow and the Variables and Call Stack sections on the left fill in.
  4. Click in the margin left of the line number of call next_colour – a red dot appears: a breakpoint.
  5. Press F5 (Continue). The program runs and stops at the breakpoint.
  6. Press F11 (Step Into) – you are inside next_colour. Keep stepping with F11 and watch A change in the Variables section; after out ($fe), a the border colour on the emulator screen changes.
  7. Hover over the word counter in the source – a tooltip shows its address and the memory content. In the Debug Console (Ctrl+Shift+Y) type m counter and press Enter.
  8. End debugging with Shift+F5 or the Stop button on the debug toolbar.

Without launch.json

For a quick try, launch.json is not required: open an .asm file in the editor (also .a80, .z80 or .s) and press F5. The extension starts the .nex and .sld of the same name from the same folder (for game.asm that is game.nex and game.sld). In this mode the program is not built – build it first (Ctrl+Shift+B or in the terminal). If VS Code asks which debugger to use (Select debugger), choose MB Maniax Next Debugger.

Program data and esxDOS. Without an SD card image, the program sees its own folder through esxDOS (loading data, saved games). A different folder or an SD card image is set in launch.json with the esxdosRoot and sdImage attributes.

In that folder the program can read and write files, delete them (also by wildcard, such as *.TMP), rename and truncate them, create and remove subfolders and set the read-only attribute. The answers and error codes are those of NextZXOS. Changes go to disk at once, and Step Back () does not undo them.

Debugging

Breakpoints

A breakpoint stops the program just before the instruction on its line is executed.

  • With the mouse: move the pointer into the narrow margin left of the line numbers – a faint red dot appears. Click to set it, click again to remove the breakpoint.
  • With the keyboard: put the cursor on the line and press F9 (toggle).
  • From the context menu: right-clicking the margin offers Add Breakpoint, Add Conditional Breakpoint… and Add Logpoint…; right-clicking an existing dot offers Edit Breakpoint…, Disable Breakpoint and Remove Breakpoint.

You can set breakpoints before debugging starts; they are sent to the emulator at startup. If there is no instruction on the line (a comment, an empty line, a label on its own), the breakpoint moves to the nearest following line with an instruction (at most 20 lines down). If there is none there either, the dot stays grey and hollow (unverified breakpoint) and its tooltip says why – for example No instruction on this line or below it (according to SLD) or SLD from sjasmplus is missing ("sld" attribute).

Paged memory. The sjasmplus SLD knows the 8K page of every line (when the source uses DEVICE ZXSPECTRUMNEXT). The breakpoint then stops only when that page is actually mapped into the corresponding MMU slot – code of another page at the same address does not trigger it. When the same line is assembled into several pages, the breakpoint applies to all of them.

If you cannot set a dot in the margin at all (nothing appears on hover), VS Code does not consider the file a language the extension reports breakpoints for. See chapter .

Stepping

While the program is stopped, control it with the debug toolbar buttons or keys:

KeyActionDescription
F5ContinueRuns until the next breakpoint, event or pause.

You can also pause and resume the program with the ⏸ / ▶ button in the emulator screen panel.

Run to Cursor and Jump to Cursor

While the machine is stopped, right-click a source line:

  • Run to Cursor – the program runs until it gets to this line (like a one-shot breakpoint).
  • Jump to Cursor – moves PC to this line without running the code in between. Useful for skipping a piece of code or repeating an instruction. If the line is assembled at several addresses (several pages), VS Code offers a choice – the items look like $C000 (page 12), and pages that are not mapped at the moment are marked not mapped.

Conditional breakpoints

A conditional breakpoint stops only when its condition holds. The condition is evaluated by the emulator itself on every pass, so it does not slow the program down – feel free to put one into a loop that runs thousands of times per frame.

  1. Right-click the margin left of the line and choose Add Conditional Breakpoint… (for an existing breakpoint Edit Breakpoint…).
  2. A small input box opens below the line. It has a drop-down on the left: leave it at Expression.
  3. Type the condition and press Enter. The breakpoint dot gets an = sign.

Example conditions:

A == 5
HL > $4000 and not ZF
mem[counter] == 3
mem16[score] >= 1000
nextreg[$50] == 10
FRAME > 100
B == 0 or (IX >= enemies and IX < enemies_end)

Labels from the source (counter, score) are written directly. The full expression language is described in chapter . An error in the condition (a typo, an unknown name) is caught by the emulator right away: the breakpoint stays grey and its tooltip shows the error. A run-time error (e.g. division by zero) is printed to the Debug Console.

Hit counts

In the breakpoint edit box choose Hit Count in the drop-down and enter which pass should stop:

EntryStops
3 or == 3exactly on the 3rd pass
>= 10on the 10th pass and every one after it
> 10, < 5, <= 5likewise
% 4on every 4th pass (4th, 8th, 12th …)

A condition and a hit count can be combined – passes are then counted only when the condition holds. The counter starts from zero whenever breakpoints change.

Logpoints

A logpoint does not stop the program; it only prints a message to the Debug Console – a debug print you do not have to write into the program. Right-click the margin and choose Add Logpoint… (or Log Message in the breakpoint edit box) and type the message. Expressions in curly braces are replaced by their values:

colour {A}, score {mem16[score]}
HL={HL:hex} DE={DE:hex} flags {F:flags}

A format may follow a colon: hex, unsigned (default), signed, char (ASCII character), bits (binary), flags (flags as SZHPNC, cleared ones as -), labels (the label at the address). A logpoint has a diamond shape in the margin. The message is printed on every pass; with a hit count, only when the count matches.

Machine event breakpoints

Some bugs are not tied to a particular line: “who keeps overwriting register $50?”, “when did the interrupt come?”. For these the extension adds event check boxes to the Breakpoints section. Ticking a box enables the event; when you hover over the item, a pencil (Edit Condition) appears on the right for entering a condition – without a condition every event of that kind stops.

All event conditions can also use registers, memory and the other names from chapter ; here PC is the address of the instruction that caused the event. The machine stops right after that instruction. Examples: REG == $50 or REG == $51, (PORT & $FF) == $FE, REG == $15 and SOURCE == CPU. After stopping on an event, its name is shown in the Call Stack header.

PORT is the full 16-bit port address as seen on the bus – for out ($fe),a the high byte is the value of A (port $01FE, $02FE …). The condition PORT == $FE would therefore stop only when A = 0. For ports decoded by the low byte only (ULA $FE, Kempston $1F …) write (PORT & $FF) == $FE; compare the full number for 16-bit ports (PORT == $243B).

Watchpoints – stopping on memory access

A watchpoint (a “data breakpoint” in VS Code) stops the program when an instruction reads or writes the chosen memory. The machine stops right after the instruction that made the access.

  • On a register: in the Variables section right-click BC, DE, HL, IX, IY or SP and choose Break on Value Change (write), Break on Value Read (read) or Break on Value Access (both). It watches the byte the register currently points to – not the register itself.
  • On a label or address: add an expression to the Watch section that is just a label name (counter) or a number ($5B00), right-click it and choose Break on Value Change.
  • With a comment in the source: ; WPMEM () – handy for areas longer than a byte and for watchpoints you want to keep.

Watchpoints are listed in the Breakpoints section, where you also disable or remove them. Newer VS Code versions also offer Add Data Breakpoint at Address in the Breakpoints section header, where you enter an address and length directly.

Expressions in Watch and on hover

You can type any expression from chapter into the Watch section: mem[counter], HL, nextreg[$07], mem16[stack_top - 2], mmu[3]. The result is shown in hex and decimal ($03 (3)). If the expression is just a label name, its address is shown together with the memory content there: $8023 (32803) → [$03] [$0003] – the byte and the 16-bit word in square brackets.

While the program is stopped, just hover over a register or label in the editor – a tooltip shows the value and the memory it points to. The tooltip appears only for words that are a valid expression.

Debug Console and memory dump

Type an expression into the Debug Console input line (Ctrl+Shift+Y, the line with > at the very bottom) and press Enter; its value is printed just like in Watch. In addition, there is a memory dump command:

m address
m address, length

Both the address and the length are expressions (a number, label, register…). Without a length, 128 bytes are dumped; the maximum is 4096. Each line has the address, 16 bytes in hex, the same bytes as text (non-printable ones as .) and the label that starts at or precedes the address:

> m start, 32
$8000  FB 31 64 80 ED 91 07 03 3E 00 32 23 80 CD 17 80  .1d.....>.2#....  start
$8010  06 19 76 10 FD 18 F6 3A 23 80 3C E6 07 32 23 80  ..v....:#.<..2#.  main_loop+3
> m HL, 16
> m stack_top - 16, 16

Viewing and editing memory

When you hover over a 16-bit register in the Variables section, a small View Binary Data icon appears on the right. It opens memory from the address in the register in the VS Code hex editor (the Microsoft Hex Editor extension – if you do not have it, VS Code offers to install it). Bytes can be overwritten in the hex editor; the write goes straight into the emulator's memory. The memory is shown as the CPU sees it (64 KB according to the current MMU mapping).

Disassembly

When the program stops outside your source (in ROM, in code without SLD, in data), or when you want to see the actual instructions, open the disassembly: right-click in the editor and choose Open Disassembly View, or run Debug: Open Disassembly View from the Command Palette. sjasmplus keywords in comments

Watchpoints, logpoints and assertions can be written right into the source as special comments (the same syntax as in DeZog). The advantage: they are part of the code, do not get lost, and work in every debug session without clicking.

SLDOPT – enabling them in sjasmplus

sjasmplus writes these comments into the SLD file only when the source contains (preferably at the beginning) the line:

    SLDOPT COMMENT WPMEM, LOGPOINT, ASSERTION

List just the words you use. sjasmplus looks for the word anywhere in the comment and is case-sensitive (write them in upper case); it does not write block comments /* */ into the SLD. A comment on a line of its own applies to the next instruction, a comment after an instruction to the instruction on the same line. In a macro the comment refers to the place the macro is invoked from.

WPMEM – watchpoint

; WPMEM [address [, size [, access [, condition]]]]
  • address – an expression; without it, the address of the line the comment is on (typically a data label).
  • size – the number of bytes watched, 1 by default.
  • access – r read, w write, rw both (default).
  • condition – optional; stops only when it holds (ADDR and VALUE can be used).
score:  dw 0            ; WPMEM            – watch the 1 byte at "score" (read and write)
buffer: ds 16           ; WPMEM buffer,16,w – stop on a write into the 16 bytes
lives:  db 3            ; WPMEM lives,1,w,VALUE == 0 – stop when zero is written
        ; WPMEM $4000, $1800, w   – any write into the ULA bitmap

After stopping, the Call Stack header shows the reason WPMEM and the Debug Console a line with the address range and the comment location, for example WPMEM $8030–$803F (game.asm:120) – WPMEM buffer,16,w.

LOGPOINT – debug print

; LOGPOINT [GROUP] text ${expression} text ${expression:format}

Prints the text to the Debug Console on every pass; ${…} is replaced by the value of the expression. The formats are the same as for VS Code logpoints: hex, unsigned, signed, char, bits, flags, labels. An optional group in square brackets right after the word is printed at the start of the line ([AI] …). The output in the Debug Console links to the source line; click it to go there.

        ld a,(hl)
        ; LOGPOINT [MAP] read ${A:hex} from ${HL:hex}
        ld (de),a

ASSERTION – assertion

; ASSERTION expression

Stops the program when the expression is false (zero). An empty ASSERTION always stops. The Call Stack header shows the reason assertion with the description ASSERTION failed: A < 10; the same text with the source location is printed to the Debug Console.

        cp 10           ; ASSERTION A < 10 – stop when the expression is false
        ; ASSERTION SP > stack_bottom and SP <= stack_top
        ret

When keywords are evaluated

LOGPOINT and ASSERTION are breakpoints at the address of their line – they are evaluated before the instruction on that line is executed. In the example ld a,(hl) ; LOGPOINT … ${A}, A would be printed before the load. To see the result of an instruction, put the comment on a line of its own below it (it then applies to the next instruction), as in the example above.

CSpect BREAK

The BREAK instruction from the CSpect emulator stops the program like a breakpoint – handy where writing a stop into the code is easier than clicking.

  • sjasmplus with --zxnext=cspect assembles BREAK as FD 00. The older CSpect DD 01 and ZEsarUX ED FF also work.
  • The machine stops just after the instruction (PC = BREAK address + 2): the yellow line is on the instruction after BREAK, the Call Stack description gives the address of the BREAK.

The Call Stack header shows the reason BREAK with the description Paused on BREAK at $8003. Continue as usual (F5, steps). Turn stopping off in launch.json: "magicBreakpoint": false.

On real hardware FD 00 runs as a NOP, but DD 01 runs as LD BC,nn and swallows the next two bytes. Don't leave DD 01 in release builds. With magicBreakpoint off, DD 01 behaves exactly as on a real Next.

Saved states

A saved state is a snapshot of the whole machine – memory, registers, hardware. It is useful when you want to return to the same place in a game repeatedly (before the boss fight, before the bug) without playing your way there every time.

Saving and restoring

  • MB Maniax: Save State… – the floppy disk button on the debug toolbar or the command from the palette. An input box Save Emulator State opens at the top; enter a name and press Enter. The same name overwrites an older state (the extension asks first).
  • MB Maniax: Restore State… – the clock button. Pick a state from the list; the machine returns to it and stays stopped (the Call Stack shows the reason state restored). Continue with F5.

States belong to the current debug session (until Stop) – they survive a Restart. There can be at most 8 of them per session. Restoring does not change breakpoints or the profiler.

States are saved at the end of a frame

The emulator can save a state only at a frame boundary. A running program is always at one, so saving while running happens immediately. If the machine is stopped in the middle of a frame (breakpoint, step), the extension asks: The machine is stopped in the middle of a frame. A state can only be saved at the end of a frame. Run to the end of the current frame and save the state there? The Run to End of Frame and Save button runs the program to the end of the frame (breakpoints are ignored meanwhile), stops (reason frame boundary) and saves the state.

Export to and import from a file

MB Maniax: Export State to File… saves the current state to a .mbxstate file, MB Maniax: Import State from File… loads it – also in another debug session. Both commands are available only in the Command Palette and only while debugging. A file can be loaded only by the same version of the extension and for the same machine type; after updating the extension, old files cannot be loaded.

Profiler

The profiler measures where the program spends its time. It adds up the T-states (CPU clock cycles) spent on every instruction and shows the result right in the source: for each line how much it cost, and with a colour how expensive it is compared to the others.

Starting

  1. While debugging, click the Start Profiler button (pulse icon) on the debug toolbar, or run MB Maniax: Start Profiler from the Command Palette. Profiler appears in the Status Bar at the bottom left.
  2. Let the program run through the part you want to measure (for example a few seconds of the game).
  3. Stop the program (F6, a breakpoint). Every time it stops, the result is shown in the open editors and the Status Bar shows the total: Profiler: 3,512,000 T.

Reading the results

  • Grey text after the end of a line, e.g. 1,234 T · 12.3 %: the line used 1,234 T-states, which is 12.3 % of all T-states during the measurement (including time outside your source). Hovering over the line repeats it in a tooltip.
  • Line background from light yellow to red: the line's cost relative to the most expensive line (8 levels). The most expensive lines are the reddest – look at them first.
  • Marks in the scroll bar on the right (overview ruler): the same colours, so you can find the expensive places even in a long file without scrolling.

A line executed many times is expensive even if the instruction itself is fast – the profiler shows the total time, not the time of one pass. Everything the CPU executes counts: waiting in HALT (every repetition) and accepting an interrupt (attributed to the instruction before which it came). Time when the CPU is held by DMA and time while paused are not counted. Instructions in a macro are attributed to the line the macro is invoked from.

Most expensive functions

MB Maniax: Show Profiler Results – from the Command Palette, or by clicking Profiler in the Status Bar – opens the list Most expensive functions, sorted from the most expensive. A function is the code from one global label to the next global label (local labels with a dot belong to their parent). Each shows the total T-states with the share, and the file and line; select one to go there. The item Outside the source code (ROM, code without SLD) at the end adds up the time spent outside your source.

Live updates, stopping, clearing

  • MB Maniax: Toggle Live Profiler Updates – results are refreshed while running too, every second. Handy when you want to see the numbers change while playing.
  • MB Maniax: Stop Profiler (button on the debug toolbar) – the measurement ends; the last results stay in the editor (even after debugging ends). A notification shows the measured total with a Show Results button; the total also stays in the status bar, and clicking it opens the list of the most expensive functions again at any time.
  • MB Maniax: Clear Profiler Data – starts counting from zero and removes the colouring. The profiler keeps running.

Tips

  • Measure only what you are interested in: run the program, get to the place, run Clear Profiler Data, let it run and stop.
  • A main loop waiting on HALT shows a large number right at the HALT – that is the free time of the frame, not a bug. The smaller HALT's share, the less headroom you have.
  • Restart and reloading the program reset the counters; the profiler stays on.
  • The profiler counts by physical address (page + offset), so paged code does not get mixed up even when it runs at the same address.

Step Back

Step Back moves the machine back by one instruction – repeatedly if you like. For this the emulator remembers the last 10 seconds of execution. It is useful when the program stops on a bug and you want to see how it got there.

Enabling it

Step Back is off by default because recording the instruction trace slows emulation down – by about a quarter on a Next at 28 MHz. Enable it in launch.json:

"rewind": true

and start debugging again. Without it, the Step Back button reports Step Back is turned off – set "rewind": true in launch.json (emulation then runs slower).

Using it

While the program is stopped, click Step Back (an arrow curving backwards) on the debug toolbar. Each click goes back one instruction; registers, memory and the picture correspond to the state before it. You can then step forward again. The Reverse button (run backwards to a breakpoint) is not available yet – it reports Reverse Continue is not available yet – use Step Back.

If the slowdown bothers you only sometimes, keep two configurations in launch.json – one with "rewind": true and one without – and pick between them in the list next to the green button in Run and Debug.

Start into NextZXOS

Normally the program is loaded straight into the emulator's memory, without an operating system. With a start into NextZXOS the emulator boots the real NextZXOS from an SD card and NextZXOS starts the program – just like on a real Next. The program then has everything NextZXOS gives it: its esxDOS, the Browser, BASIC, drivers. This is useful for programs that need NextZXOS, and to see how a program behaves when started from the Browser.

NextZXOS is not part of the debugger. The System/Next distribution (NextZXOS © Garry Lancaster, firmware, ROMs) belongs to its authors and comes under its own license ("The Next License"). The debugger therefore does not bundle it: it downloads the official distribution for emulators from specnext.com only when you ask and after you agree to the license, and keeps it only in the extension's data on your computer.

Downloading NextZXOS

Run the command MB Maniax: Download NextZXOS from the palette (Ctrl+Shift+P). You get the same offer on the first start into NextZXOS if it is not downloaded yet.

  1. The distribution's license opens, loaded from the distribution's official repository. Read it and click I agree – download. The consent is remembered; you are asked again only when the license text changes.
  2. The distribution zip (about 50 MB) is downloaded. The debugger checks its size and SHA-256 fingerprint and deletes a file that does not match.
  3. An SD card image (about 1 GB) is prepared from the zip, and from it the working card. The NextZXOS welcome program, which waits for a key, is turned off on it (the same as its D option).

Everything lives in the extension's data (globalStorage, folder nextzxos), about 2 GB in total. The default is System/Next 24.11 (NextZXOS 2.09). A newer distribution is set with mbxNext.nextzxos.url, mbxNext.nextzxos.sha256 and mbxNext.nextzxos.size (see ).

Configuration in launch.json

Add "boot": "nextzxos" to the configuration (or insert the ready-made configuration MB Maniax: Start into NextZXOS with Add Configuration…):

{
    "type": "mbx-next",
    "request": "launch",
    "name": "Debug via NextZXOS",
    "program": "${workspaceFolder}/build/game.nex",
    "sld": "${workspaceFolder}/build/game.sld",
    "esxdosRoot": "${workspaceFolder}/data",
    "boot": "nextzxos"
}

After F5:

  1. The program and the contents of esxdosRoot (without it, the folder the program is in) are copied to the card into /MBX/<program name> – here /MBX/game. Hidden files and folders (.git …) are left out; names must be ASCII.
  2. A short program is written to c:/nextzxos/autoexec.bas that goes to that folder and starts the program. Your own autoexec.bas on the card is set aside and restored after the session.
  3. The emulator boots NextZXOS (you see the whole start on the emulator screen; it takes about 8 seconds) and NextZXOS starts the program. The Debug Console says NextZXOS is starting from the SD card ….
  4. The debugger stops on the program's first instruction and only then sets the breakpoints – earlier they could hit NextZXOS code at the same addresses. From there you debug as usual.

The program's current folder is its folder on the card, so it finds its data by relative paths, as when started from the Browser.

Files the program changes

The program writes to the card, not to the folder on disk. With "syncBack": true the debugger compares the program's folder on the card with esxdosRoot when the session ends and copies new or changed files back; the Debug Console lists them. Files the program deleted on the card are only listed – they stay in the folder on disk. It is off by default, and then nothing changes on disk.

Step Back does not undo writes to the card – just like writes to disk when debugging without a card.

The working card

There is one working card for all projects; each program has its own folder in /MBX on it. To keep it from filling up with leftovers you have three options:

A breakpoint that would hit NextZXOS code does nothing during the boot – breakpoints are set only once the program has started. If NextZXOS does not start the program (a file is missing, say), you see the NextZXOS error on the emulator screen and the debugger keeps waiting; end it with Stop.

WiFi (ESP-01)

The Next has an ESP-01 WiFi module on UART 0 that programs talk to with AT commands. The debugger can emulate it: with "esp": true in launch.json the program gets a module that opens real TCP/UDP connections from your computer. That way you can debug network programs – mail, IRC, HTTP – against a server on your LAN or on the internet. The module is off by default: a program does not reach the network unless you allow it, and nothing answers it on UART 0.

Turning it on in launch.json

{
    "type": "mbx-next",
    "request": "launch",
    "name": "Debug mail with WiFi",
    "program": "${workspaceFolder}/build/mail.nex",
    "sld": "${workspaceFolder}/build/mail.sld",
    "esp": true,
    "espAllowedHosts": ["192.168.1.10"]
}

When debugging starts, the Debug Console says that WiFi is on and where the program may connect.

AttributeDefaultMeaning
espfalseTurns on the emulated ESP-01 module on UART 0.

A server on your own computer

The module always refuses loopback: the program cannot connect to 127.0.0.1 or localhost (AT+CIPSTART answers ERROR and the Debug Console shows a REFUSED … warning). LAN addresses (10.x, 172.16–31.x, 192.168.x) are allowed. So start a test server on all interfaces and point the program at the computer's LAN address (the ipconfig command shows it):

php -S 0.0.0.0:8080            → program: AT+CIPSTART="TCP","192.168.1.128",8080

How the module answers

  • The module is joined to the network JNextWifiHost from power-on: AT+CWJAP? answers +CWJAP:"JNextWifiHost",… and AT+CWJAP="network","password" accepts any network, so a program's usual connect sequence passes.
  • AT+CIPSTART over TCP answers just OK, without the CONNECT line real firmware sends. A program that waits for CONNECT would wait in vain in the emulator – let it wait for OK or ERROR.
  • Data from the server arrives as +IPD,<length>:…, a closed connection as CLOSED, as with the real module.
  • The UART speed follows the prescaler as on the Next (115,200 baud by default).

The network is outside the emulator: neither Step Back nor restoring a saved state undoes connections. While paused the module keeps receiving and the program gets the data when it runs again. WiFi also works with the start into NextZXOS.

Debugging the traffic

has a WiFi (ESP) tab. It shows everything the program sent to the module (→) and everything the module answered (←), line by line with the frame number:

  • AT commands are bold, OK green, ERROR and FAIL red, the +IPD,…: header purple; line ends show as ↵, other control characters as \xNN;
  • long data is shortened, a click on the line expands it; hovering shows the sequence number, frame, T-state and length;
  • at the top is the module's state (WiFi connection, address, allowed hosts, byte counts) and the last five connections – opened, closed, refused (a host outside espAllowedHosts or loopback), failed;
  • the toolbar has Clear, Copy (the shown lines as text), a filter, Hex and Follow (scroll to the newest line).

The debugger keeps the log all the time, even with the panel closed (up to 4 MB); a reset keeps it, a new debug session starts it afresh. The tab updates when the program stops and on Refresh, and while it runs with Live on. It replaces a communication log of your own in the program – there is no need to store the module's replies in memory and read them from there.

Two event breakpoints stop the program on a particular exchange (the Breakpoints view, see ): ESP: line sent (Z80 → ESP) and ESP: line received (ESP → Z80). They stop on the OUT or IN instruction that completed the line (with its line end), so you stand right in the code that sends the command or reads the reply. The condition here is not an expression but text the line must contain (case-insensitive), or a regular expression between slashes:

CIPSTART                 → stops on AT+CIPSTART=…
/^(ERROR|FAIL)$/         → stops when the program reads an error
/^\+IPD,\d+:/            → the first line of data from the server

Without a condition every line stops. After the stop, the line is in the stop reason description (Call Stack).

Troubleshooting

Cannot set a breakpoint – no red dot appears when hovering over the margin

VS Code allows breakpoints only in files whose language some debugger supports. This extension reports them for the languages z80-asm, asm-collection, z80-macroasm, asm, asm-x86-nasm, nasm, masm, c6510 and plaintext (Plain Text). If you have an extension for another assembler installed that claims .asm under a different language, breakpoints will not work.

  1. Look at the bottom right of the Status Bar – it shows the language of the open file (e.g. Plain Text, Z80 Assembly, ARM…).
  2. Click it. A language picker opens at the top; choose Configure File Association for '.asm'… and select a Z80 language (depending on the installed extension e.g. Z80 Assembly, Z80 Macro-Assembler) or Plain Text.

VS Code writes this into the files.associations setting. You can also write it by hand (Preferences: Open User Settings (JSON) from the Command Palette):

"files.associations": {
    "*.asm": "z80-macroasm",
    "*.i.asm": "z80-macroasm"
}

The value must be a language identifier from the list above that is available to you (plaintext always is).

The breakpoint is grey and hollow

The breakpoint is not verified. Hover over it – the tooltip says why: SLD from sjasmplus is missing ("sld" attribute) → add "sld" to launch.json; No instruction on this line or below it (according to SLD) → the line is not in the SLD (it is a comment or data, or the file was not built with this SLD); a condition error → fix the condition ().

The program does not stop at a breakpoint
  • The SLD is missing or out of date: build with --sld=… --fullpath and check that launch.json points to the same file. When starting without an SLD, the extension warns "sld" is missing in launch.json… or Cannot load SLD….
  • The paths in the SLD do not match the files in the editor: use --fullpath, or set sourceRoot.
  • You are building a different copy of the file than the one open in the editor (another folder).
  • Paged code: the breakpoint stops only when the page is mapped in (). Check which page is in the slot under Variables › Machine (MMU, time).
  • The breakpoint is disabled (unticked in the Breakpoints section), or all breakpoints are deactivated (the Toggle Active Breakpoints button in the section header).
  • The program was not rebuilt after a change – preLaunchTask is missing from launch.json, or the build failed (the Problems and Terminal tabs).
Debugging does not start
  • Program not found: … – the "program" path is wrong, or the program has not been built yet.
  • Debug server not found (…) – the extension is damaged or mbxNext.serverPath is set wrong; clear the setting, or reinstall the extension.
  • The debug server is not responding / The debug server exited during startup – try starting debugging again; details (server output) are usually in the Debug Console. An antivirus can also block the server from starting.
  • The sjasmplus task cannot be run – sjasmplus is not on the PATH ().
Choppy sound, slow emulation
  • Check Running · N frames/s in the screen bar. Below 50 the computer cannot keep up.
  • Turn off Step Back ("rewind": false) – the instruction trace slows things down by about a quarter.
  • Turn off Live in the Next panel and live profiler updates; close the Next panel when you do not need it.
  • Logpoints printing thousands of times per second slow down the Debug Console – use a hit count (% 50) or a condition.
  • The screen panel redraws only while it is visible; hidden behind another tab it costs nothing.
The screen panel or the Next panel disappeared

The panels are editor tabs: look for them in another tab group, or open them again – MB Maniax Next: Show Emulator Screen and MB Maniax: Next Panel (Sprites, Palettes, …).

The keyboard does not work in the emulator / shortcuts do not work in VS Code

Keys go to the emulator only while the screen has the focus (click into it). Conversely, VS Code shortcuts (F5, F10) work only when the screen does not have the focus – click into the editor.

No sound

Click the screen or the 🔇 button – sound may start only after a click. Check that the program is running (it is silent while paused) and that the icon shows 🔊.

The extension speaks a different language than I want

Set mbxNext.language () and start debugging again. Command names and the descriptions in Settings follow the VS Code display language (the Configure Display Language command), not this setting.

The old version still runs after an update

Stop debugging and reload the window: Ctrl+Shift+P → Developer: Reload Window ().

A saved state file cannot be imported

A .mbxstate file can be loaded only by the same version of the extension and for the same machine type (machine).
